## ConfigureScaleUpFabricManager

`rack_manager.RackManager/ConfigureScaleUpFabricManager`

ConfigureScaleUpFabricManager performs complete ScaleUpFabricManager configuration on a switch. This includes enabling the scale fabric services services,configuring gRPC access,and sets multi-node scaleup topology based on the hardware platform. Credentials are resolved from the node's stored inventory data.

<Warning>
This is the single-switch version. For declarative configuration of a whole fabric, use `RackManagerV2/ConfigureScaleUpFabricManager`.
</Warning>

## InspectScaleUpFabrics

`rack_manager.RackManager/InspectScaleUpFabrics`

InspectScaleUpFabrics discovers enabled controllers and reports their live compute and switch members, control-plane state, and sampled component status. Compute BMCs provide physical identities for correlating observed GPUs with caller node IDs; compute hosts are not configured or tested. No devices are changed. Results do not verify a desired configuration, end-to-end communication, or bandwidth.

<Warning>
This server returns UNIMPLEMENTED for live multi-fabric inspection.
</Warning>

| Field | Type | Description |
| --- | --- | --- |
| `nodes` | [`NodeSet`](types-rack-manager.md#nodeset) | Include the switches to inspect and, optionally, compute trays to identify in the results. At least one switch is required. Node IDs must be nonempty and unique. RMS uses NodeInfo.type when set to a value other than NODE_TYPE_UNSPECIFIED. Otherwise, RMS uses node_descriptor to identify the node's role. Unknown or unsupported node roles are rejected. Each switch needs host_endpoint and credentials. Each compute entry represents one tray and needs bmc_endpoint and credentials to read chassis and tray positions. RMS reads compute BMCs for discovery; it does not configure compute hosts. ## BatchResetSwitchSdnFactoryDefault

`rack_manager.RackManager/BatchResetSwitchSdnFactoryDefault`

BatchResetSwitchSdnFactoryDefault submits asynchronous SDN factory-default resets. All switches in the request use the same domain for switch mTLS material. Returns a parent job ID. Use GetJobStatus with child job states to track per-node progress. The reset is idempotent; callers can retry after transport or service failure. Note: post hard reset, the scale-up fabric must be reconfigured.

<Warning>
This operation is destructive. After a reset, reconfigure the scale-up fabric.
</Warning>

| --- | --- |
| Execution | **Asynchronous, parent and child jobs.** The response returns a parent job ID and the work continues after the call returns. |
| Job tracking | Poll [`GetJobStatus`](utility-jobs.md#getjobstatus) with the job ID in `response.job_id`. Set `include_child_job_states` on `GetJobStatus` to read per-node child jobs. |

## ConfigureScaleUpFabricManager (V2)

`rack_manager_v2.RackManagerV2/ConfigureScaleUpFabricManager`

ConfigureScaleUpFabricManager declaratively configures the scale-up fabric across all supplied switches. The caller describes the desired fabric configuration and RMS starts a single asynchronous reconciliation job that performs only the actions required to move the observed switch state toward the desired state: it skips disabling the fabric when it is already disabled, and does nothing when the observed configuration matches the request and controller activation is verified.

The call is safe to invoke periodically in a loop to keep switch configuration "as intended" without causing fabric availability issues. RMS aims to run one reconciliation job at a time; callers should poll GetJobStatus before resubmitting and avoid issuing concurrent ConfigureScaleUpFabricManager requests.

Without layout, requests with an empty topology_type or otherwise invalid config are rejected synchronously with INVALID_ARGUMENT; no job is started.

Returns a job_id; poll it via rack_manager.GetJobStatus. Without layout, successful jobs return JSON-encoded rack_manager.ScaleUpFabricStatus in rack_manager.JobStatus.result_json.

With layout, the resulting configuration contains one cluster and primary per fabric, with administrative switch connectivity matching the requested layout. Submit the complete desired fabric set in one request because the fabrics share switch connectivity settings. GetJobStatus reports execution state and errors. InspectScaleUpFabrics reports current fabric members and sampled component status, including partial configurations after a failed job. Completion requires verified administrative switch settings and configured fabric-manager control planes, not compute software or operational GPU links.

<Warning>
Layout requests require matching deployment rules and the complete physical switch inventory. Without layout, RMS validates every node ID and type, then configures only switches.
</Warning>

| Property | Value |
| --- | --- |
| Execution | **Asynchronous, one job.** The response returns a job ID and the work continues after the call returns. |
| Job tracking | Poll [`GetJobStatus`](utility-jobs.md#getjobstatus) with the job ID in `job_id`. |
| Job result | `result_json` in the job status holds a JSON-encoded `ScaleUpFabricStatus` for successful no-layout and full-capacity layout jobs; partial layouts use `InspectScaleUpFabrics` for live status. |
| Target | **Caller-supplied nodes.** The request carries each node's endpoints and credentials, and RMS does not store them. |
| Behavior details | [Operations guide](../../operations/switch-management.md) |
| Protobuf reference | [`ConfigureScaleUpFabricManager`](/rms/api-reference/protobuf-reference/rack-manager-v-2/rack-manager-v-2/rack-manager-v-2-configure-scale-up-fabric-manager) |

**Request:** [`ConfigureScaleUpFabricManagerRequest`](types-rack-manager-v2.md#configurescaleupfabricmanagerrequest)

| Field | Type | Description |
| --- | --- | --- |
| `nodes` | [`NodeSet`](types-rack-manager.md#nodeset) | Without layout, RMS validates all nodes and configures only switches; other recognized node types are ignored. With layout, include every physical switch, even switches outside the requested fabrics, and compute trays for selection. At least one switch is required, and node IDs must be nonempty and unique. RMS uses NodeInfo.type when set to a value other than NODE_TYPE_UNSPECIFIED. Otherwise, RMS uses node_descriptor to identify the node's role. Every node must resolve to a supported type. With layout, only switch and compute nodes are accepted. The order of nodes does not determine which fabric they belong to. Each switch needs host_endpoint and credentials. With layout, each compute entry represents one tray and needs bmc_endpoint and credentials for reading its position. RMS reads compute BMCs for layout discovery; it does not configure compute hosts. Compute entries are required unless layout requests one fabric covering the full physical compute and switch capacity. For that layout, either omit all compute entries or include every compute tray. Omission avoids compute BMC reads. For other layouts, compute trays outside the requested fabrics may be omitted. |
| `primary_switch_node_id` | optional `string` | ID of the switch node that should run the fabric manager (the primary host). If absent, RMS selects the switch at the lowest position in the rack. |
| `domain` | optional `string` | Selects the CA and RMS client credentials for all switches in this request. If omitted, RMS uses --default-switch-domain. TLS server-name verification uses each endpoint's identity or the configured DNS override, not this value. |
| `config` | [`ScaleUpFabricConfig`](types-rack-manager-v2.md#scaleupfabricconfig) | Desired scale-up fabric configuration to reconcile the switches toward. With layout, caller settings are shared by selected fabrics; managed static values can differ by fabric size. |
| `layout` | [`ScaleUpFabricLayout`](types-rack-manager-v2.md#scaleupfabriclayout) | Optional arrangement of independent fabrics within the supplied inventory; fabric sizes may differ from the complete physical topology. Supply the complete desired fabric set in one call to coordinate shared links. Requires config and at least one fabric; primary_switch_node_id must be absent. One fabric matching the complete physical compute and switch capacity restores full connectivity and one controller cluster. Other layouts isolate unused capacity. When absent, one cluster is configured without changing managed link settings. |

**Response:** [`ConfigureScaleUpFabricManagerResponse`](types-rack-manager-v2.md#configurescaleupfabricmanagerresponse)

| Field | Type | Description |
| --- | --- | --- |
| `job_id` | `string` | ID of the asynchronous job that reconciles the scale-up fabric. Poll it via rack_manager.GetJobStatus. Read live fabric members and component status via rack_manager.InspectScaleUpFabrics. Successful no-layout jobs also return JSON-encoded rack_manager.ScaleUpFabricStatus in result_json. |
| `selected_fabrics` | repeated [`ScaleUpFabricMembers`](types-rack-manager-v2.md#scaleupfabricmembers) | Empty without layout. With layout, identifies the nodes and primary selected for each requested fabric, in request order. Selection does not indicate that configuration has completed; use job_id to track execution. |

**Errors:** Refer to [Conventions](../conventions.md#error-handling) for how RMS reports failures. This RPC also returns these gRPC errors:

- `INVALID_ARGUMENT`: The topology, inventory, or layout request is invalid. No job starts.
- `FAILED_PRECONDITION`: Physical discovery, deployment planning, or switch ownership prevents admission. No configuration worker starts.
- `INTERNAL`: Job admission or coordinator state fails internally. No configuration worker starts.
- `UNIMPLEMENTED`: Layout configuration has no installed deployment catalog or the switch family is unsupported. No job starts.
